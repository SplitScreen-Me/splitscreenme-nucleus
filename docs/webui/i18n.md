# Translations (i18n)

How Nucleus Co-op shows its texts in several languages: the language files, the C# runtime (engine, services, host), the bridge, the web UI runtime, and the checks. English is the source language; every other language falls back to English, key by key.

```
Master/i18n/en.json  ──copied by Nucleus.Coop.csproj──▶  <install>\i18n\en.json, fr.json…
   │  (also built into Nucleus.Gaming.dll, and into the UI bundle)
   ├──▶ C#: Nucleus.Gaming.Localization (I18n.T)  ── host texts (settings labels, notices, prompts, overlay…)
   │                                                     └─ reach the UI already translated, through the bridge
   └──▶ UI: src/i18n (t, <T>, format)            ◀── i18n.getState / getStrings / setLanguage, i18n.languageChanged
```

## The language files

One file per language in `i18n\` next to `NucleusCoop.exe`, named after its language tag: `en.json`, `fr.json`, `pt-BR.json`, `zh-Hant.json`. The source of truth is `Master/i18n/` in the repo; the `CopyI18n` target of `Nucleus.Coop.csproj` copies it to the output (`bin\Debug\i18n\`, `bin\Release\i18n\`), so packages built from `bin\Release` carry it. **The languages the app offers are the files it finds there**: adding a language is adding a file.

```json
{
  "_meta": { "locale": "fr", "englishName": "French", "nativeName": "Français", "direction": "ltr" },
  "common": { "ok": "OK", "cancel": "Annuler" },
  "shell": {
    "titleBar": {
      "freeDevices_one": "{count} libre",
      "freeDevices_other": "{count} libres",
      "player": "Joueur {number} : {devices}"
    }
  },
  "lobby": { "lockHint": "Appuyez sur <kbd>{key}</kbd> pour verrouiller" }
}
```

- JSON objects nested by namespace, strings as leaves. Code uses the dotted key: `shell.titleBar.player`.
- `_meta` is required: `locale` (= the file name), `englishName`, `nativeName` (shown in the language picker), `direction` (`ltr` by default, `rtl` for Arabic or Hebrew).
- Properties whose name starts with `_` are not translated strings: `_meta`, and notes for translators (`"_note": "…"`), anywhere.
- A missing key shows in English. A broken or missing file means English (the C# log says why: `[i18n] …`). If `en.json` itself is missing, C# uses the copy built into Nucleus.Gaming and the UI its own: the app still works, which is why `StartChecks` does not require the file.
- Encoding: UTF-8. The repo is CRLF in the working tree; JSON doesn't care.

### Key naming

- `namespace.area.name`: the first segment is the **namespace** (who owns it, below), then the screen, component or area, then a short semantic name: `library.gameMenu.openFolder`, `lobby.steps.optional`, `host.settings.fields.misc.useNicknames.label`.
- Segments are camelCase and start with a lowercase letter (`^[a-z][a-zA-Z0-9]*$`). Plural forms add a suffix to the last segment: `_zero`, `_one`, `_two`, `_few`, `_many`, `_other`.
- Name what the text **is**, not what it says: `deleteProfile.confirmLabel`, not `deleteProfile.yesDeleteIt`. Changing an English text keeps its key; changing its meaning gets a new key (old translations must not survive a change of meaning).
- One key per use: don't reuse a string because the English happens to match, except the deliberate generic words of `common` (`common.cancel`, `common.save`…). A word can translate differently in another place ("Open" a menu vs "Open" a folder).
- Don't split sentences into several keys and don't glue translated fragments together: one key for the whole sentence, with placeholders. Word order changes between languages.
- A key is a string or a namespace, never both; plural keys have only plural forms (`x_one`, `x_other`, never also `x`).

### Namespaces and owners

| Namespace | What | Owner |
|---|---|---|
| `common` | generic words the UI repeats (OK, Cancel, Close, Save, Retry…), error wording (`common.errors.*`), time phrases | core, ui-common |
| `shell` | title bar, rail, hint bar, command palette, offline banner, startup screens | core, ui-common |
| `ui` | design-system components (`src/ui`) | core, ui-common |
| `features` | cross-screen flows (`src/features`: add a game, drop a file, notices) | core, ui-common |
| `language` | the first-launch picker | core |
| `library`, `catalog`, `handler`, `downloads`, `hub` | library screen, Get games, handler page, downloads, hub data wording (`src/hub`) | ui-library |
| `lobby`, `setup`, `profiles` | lobby screen, setup flow, profiles dialogs | ui-lobby |
| `session`, `settings` | session screen; the **web** settings screen chrome (not the C# catalog) | ui-session-settings |
| `host` | C# services: settings catalog labels, descriptions and choices (`host.settings.*`), user-facing errors (`BridgeException` messages), notices, setup hints and checks | host-services |
| `engine` | Nucleus.Gaming and the NucleusCoopTool host: `UserPrompts`, launch overlay, OSD toasts, start checks, tray, native dialogs | engine |

An extractor fills its own namespaces and only those; a missing generic word goes to `common` through its owner.

### Placeholders

`{name}`: letters, digits and `_`. The code passes every value; a translation may move placeholders but must keep them all (and add none): `i18n:check` fails otherwise.

- Numbers passed as numbers are formatted for the language (`1,234` / `1 234`). Pass a string to print digits as they are (years, ids, versions): `{ year: String(year) }`.
- A placeholder without a value stays visible as `{name}`: a missing argument shows instead of vanishing.
- Values are never parsed: a game name containing `<b>` prints as is.

### Plurals

A string that depends on a number has CLDR plural forms and takes a numeric `count`:

```json
"gameCount_zero": "No games",
"gameCount_one": "{count} game",
"gameCount_other": "{count} games"
```

```ts
t('library.gameCount', { count: games.length })
```

- The form is chosen by the language's rules: `Intl.PluralRules` in the UI, `PluralRules` in C# (same answers, checked against the same cases: `src/bridge/__tests__/fixtures/plurals.json`). English uses `one` and `other`; French `one` (0 and 1), `many` (exact millions) and `other`; Russian `one`, `few`, `many`, `other`; Japanese only `other`.
- `_zero` is optional and wins for 0 in any language (for "No games" rather than "0 games").
- `_other` is required. A translation provides the forms of **its** language (French adds `_many`, Japanese keeps `_other` only); English keys decide which strings are plural.
- The other forms may drop `{count}` ("One game").

### Rich text

Markup goes inside the string as tags, never as HTML and never by concatenating pieces:

```json
"lockHint": "Press <kbd>{key}</kbd> to lock the inputs, <b>then</b> play."
```

```tsx
<T k="lobby.lockHint" values={{ key: 'End' }} />
<T k="handler.byAuthor" values={{ author: <a href={url}>{name}</a> }} tags={{ b: (c) => <strong className="text-ink">{c}</strong> }} />
```

- Tags: `<name>…</name>` and `<br/>`. App-wide renderers: `b`, `strong`, `i`, `em`, `code`, `br`, and `kbd` as the design system's `Kbd` (`App.tsx` passes it to `I18nProvider`). A tag nobody renders shows its content only. `tags` on `<T>` overrides per string (links, colours).
- The template is parsed into React elements; placeholders are filled in afterwards, so values can't inject markup. Nothing goes through `innerHTML`.
- `t()` on a rich string returns plain text (tags dropped), for `title`, `aria-label` or toasts. In C#, `I18n.TPlain` strips them for native windows.
- Translations must keep the same tags (`i18n:check`).

## What is translated

**Translated**: every text a user can see or hear: JSX text, button labels, titles and tooltips, `aria-label`s, placeholders, `alt` texts, toasts, dialogs, hints, empty states, error messages shown to users, settings labels, descriptions and choices built in C#, notices, native prompts (`UserPrompts`), the WPF launch overlay and OSD toasts, start-up check messages, tray and menu texts, the document title.

**Not translated**:
- log lines (debug-log, app.log, handler logs, `ServiceLog`, `console.*`), and exception messages that only developers see;
- what handlers and the hub provide: handler descriptions and notes, game names, hub data, comments;
- file and folder names, paths, settings values stored in Settings.ini, ids;
- key caps when they name a physical key (`Ctrl`, `End`, `F5`, gamepad buttons `A`, `LB`): the words around them are translated (`Press <kbd>{key}</kbd> to lock`);
- brands: Nucleus Co-op, SplitScreen.Me, Steam, Epic, GOG, Xbox, PlayStation, Discord, GitHub, Windows…;
- the Steam / Epic emulator languages (`misc.steamLanguage`, `misc.epicLanguage`): they are what the game sees, unrelated to the app's language.

## Web UI (`src/i18n`)

```tsx
import { T, useI18n, useT } from '@/i18n';

function Chip({ count, names }: Props) {
  const { t, format } = useI18n();                  // or: const t = useT();
  return (
    <span title={t('shell.titleBar.freeDevicesHint', { names: format.list(names) })}>
      {t('shell.titleBar.freeDevices', { count })}
    </span>
  );
}
```

| API | Use |
|---|---|
| `useI18n()` | `{ t, format, locale, rtl, state, setLanguage, tags }`; the component re-renders when the language changes. `state` is the host's `LanguageState` (languages, detected, chosen). |
| `useT()` | Just `t`, re-rendering on a change. |
| `t(key, params?)` | Plain text in the language in use. **Typed**: an unknown key, a missing or unknown placeholder, a wrong `count` type are compile errors (`src/i18n/generated/keys.ts`). |
| `<T k values tags />` | Rich strings (tags) and element values. |
| `<RichText text values tags />` | A string with tags that the host built (a setup hint, a notice). |
| `format.*` | `number`, `percent`, `compact` (508K), `bytes` (1.5 MB, 1024 based), `date` (`short`/`medium`/`long`/`full` or Intl options), `time`, `dateTime`, `ago` ("3 days ago"), `when` ("yesterday", "in September"), `duration` (seconds → "2 hr 14 min"), `clock`, `list` ("A, B, and C"). Always Intl, never hand-built; a language tag Intl doesn't know gets English Intl data (`intlLocale`), not the Windows language. |
| `t`, `format`, `tDynamic` from `@/i18n` | Outside React: event handlers, `src/lib`. They read the language in use but don't re-render anything: in components, use the hooks. |
| `isMessageKey(k)`, `tDynamic(k, params)` | Keys computed at runtime. Prefer a typed map (`Record<Level, MessageKey>`), which keeps the checks. |

- `src/lib/format.ts` (`fmtCount`, `fmtDate`, `fmtWhen`, `fmtDuration`, `listJoin`…) delegates to these formatters, so existing screens already follow the language; `plural()` is English-only and deprecated: use a plural key.
- English is built into the bundle (`src/i18n/english.ts` imports `Master/i18n/en.json`): screens before the bridge handshake (splash, version mismatch, host down) have texts, and `npm run dev` hot-reloads `en.json`. Other languages come from the host (`i18n.getStrings`, the file's own strings); the UI falls back to the bundled English per key.
- `I18nProvider` (in `App.tsx`, inside `BridgeProvider`) follows the host's language: it loads the strings, sets `<html lang dir>`, keeps the last language's strings in localStorage (`nucleus.i18n`) so the next start shows its first screen in that language, and on `i18n.languageChanged` refetches **every** bridge query (host texts are built in the language in use).
- Missing keys print a console warning once (`[i18n] missing string …`) and show the key.

### Adding a string (web UI)

1. Add it to `Master/i18n/en.json` under your namespace.
2. `npm run i18n:gen` (updates `src/i18n/generated/keys.ts`; `npm run dev` picks up `en.json` by itself, the types need the generator).
3. Use it: `t('library.gameMenu.openFolder')`.
4. `npm run i18n:check` and `npm run typecheck`.

## C# (`Nucleus.Gaming.Localization`)

The runtime lives in Nucleus.Gaming, the lowest layer, so the engine, the services and the host share it.

```csharp
using static Nucleus.Gaming.Localization.I18n;

string title = T("engine.startChecks.missingFile.title");
string text = T("engine.startChecks.missingFile.message", new { file });        // {file}
string count = T("library.gameCount", new { count = games.Count });             // gameCount_one / _other
MessageBox.Show(TPlain("engine.x.message"), …);                                 // tags stripped for native windows
CultureInfo culture = I18n.Culture;                                             // format dates and numbers for the user
I18n.LanguageChanged += (s, e) => …;                                            // rebuild cached texts
```

- `I18n.T(key, args)`: the language in use, English for missing keys, the key itself (logged once) when English lacks it too. `args` is an anonymous object or a dictionary; a numeric `count` picks the plural form (same rules as the UI). Numbers are formatted with the language's culture.
- `I18n.Initialize()` runs first thing in `Program.RunApplication` (before the start checks): saved language (Settings.ini `[Misc] AppLanguage`), else the Windows display language (`LanguageDetector`: exact tag, then parent, then another region of the same language, then English). Other processes (StartGame.exe…) initialize on first use the same way.
- **Process cultures are never changed**: handlers parse numbers with `CurrentCulture`. Format user-facing values with `I18n.Culture` or pass them as arguments.
- Thread-safe: lookups read an immutable snapshot; `SetLanguage` swaps it and raises `LanguageChanged` on the calling thread.
- `Translator` is the instance behind the facade (tests create their own on a temporary folder); `PluralRules` has the rules of about forty languages (English, Germanic, Romance, Slavic, CJK, Turkish, Arabic… see the file) and uses the English rule for the others; `PluralRules.Register` adds one; `MessageFormat` has the placeholder and tag helpers.
- In a generic class whose type parameter is `T`, write `I18n.T(…)`.

### Texts built by the host

Host texts reach the UI already translated: a DTO string is built with `T()` **when the answer is built**, in the language in use. After a change of language the UI refetches every query, so anything built per request follows. Rules for the `host` and `engine` extractors:

- Build texts at request time, not in constructors or static fields. What must be cached is rebuilt when the language changes: `SettingsService` keeps its catalog per language (see `SettingsCatalog.Sections`, now a property, and the General section and language field as the pattern).
- Expected failures: `throw new BridgeException(kind, T("host.handlers.errors.notFound"), data)`; the UI shows `message` as is. Keep `data.reason` codes for logic.
- Texts already sent and kept (a notice waiting to be read, a session log line) stay in the language they were built in.
- Strings with tags meant for the UI are rendered with `<RichText>`; native windows use `TPlain`.
- `npm run i18n:check` checks that every literal key of `T("…")` / `TPlain("…")` in the C# code exists in `en.json`.

## The bridge (`i18n` service)

| Method / event | |
|---|---|
| `i18n.getState()` → `LanguageState` | `current`, `detected` (matching Windows), `chosen` (false until the user picks one), `languages` (`locale`, `englishName`, `nativeName`, `rightToLeft`, `completion` 0-100). |
| `i18n.getStrings({ locale })` → `LanguageStrings` | The file's own strings, flattened, without English. `notFound` for an unknown language. |
| `i18n.setLanguage({ locale })` | Saves to Settings.ini and switches. `invalidParams` for an unknown language. |
| `i18n.languageChanged { locale }` | After any change (this method, Settings, code). Invalidates `i18n.getState` and `i18n.getStrings`; `I18nProvider` refetches the rest. |

Registered before the library services (`NucleusServices.Register`), so the page gets its strings at once. The mock (`src/bridge/mock/i18n.ts`) serves English and **`en-XA`, a pseudo-language** (`[Šéţţîñĝš ~~]`, accented and 30 % longer): pick it in Settings with `npm run dev` and every text that skips `t()` stands out in plain English, long translations included. The mock's own host texts stay English. Its choice is kept in `localStorage['nucleus.mock.language']`: remove it to see the first-launch picker again.

## Choosing the language

- **First launch**: Settings.ini ships `AppLanguage=` empty. Until a language is saved, the app runs in the detected one and the shell shows the picker (`src/features/language.tsx`): the available languages by native name, the detected one preselected and focused, "Your Windows language" on it, the share translated when below 100 %. Mouse, keyboard (arrows, Enter) and gamepad (D-pad, A) work like the rest of the UI; Escape, B or the close button keep the selected language. Notices wait until it is closed.
- **Settings > General > Language**, the first setting: a choice field of the C# catalog (`misc.appLanguage`, choices from the i18n folder, labels like "Français (French)"). Saving it switches the app at once: the UI re-renders, the settings schema and other host texts are fetched again.
- The saved value is the locale tag; a saved language whose file disappeared counts as not chosen (the picker shows again).

## Adding a language

1. Copy `Master/i18n/en.json` to `Master/i18n/<tag>.json` (`fr`, `pt-BR`…), set `_meta` (`locale` = file name, `englishName`, `nativeName`, `direction`).
2. Translate the values; delete the ones you don't translate yet (they show in English). Keep keys, placeholders and tags; use the plural forms of the language (`_one`, `_few`, `_many`, `_other`…).
3. `npm run i18n:check`: unknown keys, placeholder or tag differences, plural misuse, a bad `_meta` fail; the coverage of each language is printed.
4. If C# has no plural rule for the language, add it to `PluralRules` (and its cases to `fixtures/plurals.json`).
5. Build: the file is copied to `i18n\`, the language appears in Settings and in the first-launch picker. A translator can also drop the file into an installed `i18n\` folder and restart Nucleus. The host reads the folder again whenever its files change, so switching to another language and back loads an edited file without a restart.

## Checks

Run from `Master/Nucleus.WebUI`, with the other verifications (`bridge:check`, `typecheck`, `test:bridge`, `build`):

| Command | Fails when |
|---|---|
| `npm run i18n:gen` | (writes `src/i18n/generated/keys.ts` from `en.json`; refuses a malformed `en.json`) |
| `npm run i18n:check` | `keys.ts` is stale; `en.json` breaks the rules (names, plural forms, tags, `_meta`); another language has keys English doesn't, other placeholders or tags, plural misuse, a bad `_meta`; a C# `T("…")` key is not in `en.json` |
| `npm run typecheck` | a `t()` / `<T>` key doesn't exist, or its values don't match its placeholders |
| `npm run i18n:lint` | reports hard-coded user-visible strings in `src` (JSX text; `title`, `aria-label`, `placeholder`, `alt`, `label`… props; `label:`, `title:`, `message:`, `hint:`… properties; `toast()` calls; `document.title`), counted by folder. `--list` prints each one, paths filter (`npm run i18n:lint -- --list src/shell`), `--max=N` fails above N (for CI once extraction is done), `--json` for tools. `src/bridge` and `src/i18n` are not scanned. |
| `npm run test:bridge` | the engine, formatters, checks, linter and mock tests (`src/bridge/__tests__/i18n-*.test.ts`) |
| `dotnet test …Nucleus.Coop.Services.Tests.dll` | the C# loader, fallback, plurals, detection and service tests (`Localization/`) |

The linter is a heuristic on the AST. When a string is right as it is (sample data, a symbol, a debug screen), say so where it is: `{/* i18n-ignore: brand name */}` or `// i18n-ignore: …` on the line or the line before; `// i18n-ignore-file: …` for a whole file.
